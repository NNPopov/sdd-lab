# 0043 · build_cc_decomposition — Requirements

## Functional Requirements

| ID | Requirement |
|---|---|
| F1 | `ValidationFailure` shall be a sealed class with two concrete subtypes: `FieldValidationFailure({required Map<String, String> fields})` and `MessageValidationFailure({required String message})`. |
| F2 | `create_user_adapter` shall emit `MessageValidationFailure` for HTTP 422 responses; the adapter shall not attempt to parse a FastAPI `detail` list for this endpoint. |
| F3 | `create_tier_adapter` shall emit `MessageValidationFailure` for HTTP 422 responses. |
| F4 | `update_user_adapter` shall parse the FastAPI `detail` list into a `Map<String, String>` and emit `FieldValidationFailure(fields: {...})` for HTTP 422 responses. |
| F5 | `UpdateUserUseCase` shall emit `FieldValidationFailure(fields: {'_form': 'Nothing to update'})` for the empty-update guard so that `EditUserForm` routes the error to the form-level slot. |
| F6 | `CreateUserState` shall expose a `validationError({required String message})` variant and a `conflict({required String message})` variant in addition to the existing `idle`, `submitting`, `success`, and `failure` variants. |
| F7 | `CreateUserCubit.submit()` shall emit `CreateUserValidationError` when the use-case returns `MessageValidationFailure`, `CreateUserConflict` when it returns `ConflictFailure`, and `CreateUserFailure` for all other failure types. |
| F8 | The Create User screen shall render the server validation message as a styled error text block below the submit button when the Cubit state is `CreateUserValidationError`. |
| F9 | The Create User screen shall display no `errorText` on any `TextFormField` for server-side validation errors; field-level `errorText` is reserved for client-side validators only. |
| F10 | The Create User screen's `TextFormField` validators shall check only client-side constraints (non-empty, email format, password minimum length) and shall not read Cubit state or widget-local error maps. |
| F11 | The Create User screen's `BlocConsumer` listener shall handle `CreateUserSuccess` (snackbar + pop), `CreateUserConflict` (snackbar with server message), and `CreateUserFailure` (generic snackbar); `CreateUserValidationError` shall have no listener case and shall be handled entirely in the builder. |
| F12 | The Create Tier screen shall match `MessageValidationFailure` when rendering the validation error text below the submit button and in the listener's break case. |
| F13 | The Edit User screen shall route `FieldValidationFailure.fields` to `EditUserForm` as `serverErrors`; the per-field display and clear behavior shall remain unchanged. |
| F14 | `UserActionVisibility.from(Set<Permission> permissions, AuthState auth, String username)` shall derive `isMe`, `showEdit`, `showDelete`, `showErase`, `canEditTier`, and `canManageModerators` in a single pure computation. |
| F15 | `UserActionVisibility.from` shall return `showEdit: true` and `showDelete: true` only when `isMe` is true; `showErase: true` only when `permissions` contains `Permission.eraseUsers`. |
| F16 | `UserActionVisibility.from` shall return `canManageModerators: true` only when `permissions` contains `Permission.manageModerators`; `canEditTier: true` only when `permissions` contains `Permission.editUserTier`. |
| F17 | The `UserDetailsScreen` AppBar actions shall rebuild reactively when either `PermissionCubit` state or `AuthCubit` state changes. |
| F18 | `AssignModeratorButton` inside `UserDetailsScreen` AppBar shall be shown only when `canManageModerators` is true and `UserDetailsCubit` has loaded the user; the `isModerator` value shall be derived from the loaded user state. |
| F19 | `PostDetailsScreen.build()` shall construct only the `Scaffold` skeleton and shall delegate AppBar action rendering to `_PostDetailsActions` and body rendering to `_PostDetailsBody`. |
| F20 | `_PostDetailsActions` shall show edit and delete buttons when the authenticated user is the post author, and the erase button when the user is a superuser and not the author. |
| F21 | `_PostDetailsBody` shall render a `CircularProgressIndicator` for loading state, an error message with a retry button for error state, and the post content for loaded state. |
| F22 | `_PostDetailsBody` shall show `PostStatusChip` in the loaded branch only when the authenticated user is the post author. |

## Non-functional Requirements

| ID | Requirement |
|---|---|
| N1 | `ValidationFailure` extends `Failure` directly as a `sealed class` declared in `failure.dart`; `FieldValidationFailure` and `MessageValidationFailure` are `final class` without `freezed` generation. |
| N2 | `CreateUserState` is a `sealed class` generated by `freezed`; the new `validationError` and `conflict` variants follow the same `const factory` pattern as existing variants. |
| N3 | After the `ValidationFailure` type change, no call site accesses the former `ValidationFailure.fieldErrors` property; every consumer pattern-matches the specific subtype it expects. |
| N4 | `UserActionVisibility` is a non-private `final class` located in `lib/features/users/user_details/presentation/user_action_visibility.dart`; it carries no mutable state and is testable without rendering any widget. |
| N5 | `_UserDetailsAppBarActions` uses `context.select` for all three reactive sources (`PermissionCubit`, `AuthCubit`, `UserDetailsCubit`); `context.read` is used only inside callbacks (button `onPressed`, `onToggled`). |
| N6 | `_PostDetailsActions` and `_PostDetailsBody` are private `StatelessWidget` subclasses defined in `post_details_screen.dart`; they are not registered with `get_it` or `injectable`. |
| N7 | The `CreateUserScreen` `BlocConsumer` listener contains no nested `switch` expression; each observable state maps to exactly one top-level `case`. |
| N8 | `_CreateUserScreenState` contains no `setState` calls; Cubit state is the single reactive source for all error and loading display. |
| N9 | All UI strings in modified presentation files are accessed via `slang` (`context.t`); no hardcoded strings are introduced. |
| N10 | Each modified adapter retains the double-catch pattern: `on DioException` inner catch and `on Object catch (e, st)` outer catch with `_logger.error(...)`, per `agent_docs/error_handling.md`. |
| N11 | No cross-feature imports are introduced; `UserActionVisibility` is imported only within the `user_details` slice presentation layer. |
| N12 | `UpdateUserUseCase` resides in `domain/`; its only import is `FieldValidationFailure` from `core/errors/failure.dart` which is pure Dart — no `flutter/*` or `dio/*` imports are added. |
| N13 | `dart run build_runner build --delete-conflicting-outputs` regenerates `failure.freezed.dart` and `create_user_state.freezed.dart` after the type changes. |
| N14 | `dart analyze --fatal-infos` passes with zero warnings after all changes land. |
| N15 | `dart format .` produces no diff after all changes land. |

## Out of scope

- `CreateTierScreen` `setState` + Cubit fix (covered by slice 0042).
- `AssignModeratorButton` `setState` fix (covered by slice 0042).
- WARNING-level SLOC violations in `build()` methods below the ALARM threshold.
- `_mapHttp` cyclomatic-complexity warnings in adapters.
- Changes to server API contracts or response parsing beyond the `ValidationFailure` type change.
- `UserDetailsScreen` body section CC reduction beyond what falls naturally from the AppBar extraction.
- Adding explicit `validationError`/`conflict` state variants to `CreateTierState`.
