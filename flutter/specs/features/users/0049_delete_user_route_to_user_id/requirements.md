# 0049 · delete_user_route_to_user_id — Requirements

## Functional Requirements

| ID | Requirement |
|---|---|
| F1 | A signed-in user can delete their own account, and the delete action issues `DELETE /user/{user_id}` with the integer user id. |
| F2 | Deletion of an account whose id does not match the current user's id is refused and the delete API is never called. |
| F3 | A successful self-delete logs the user out locally without showing the global "session expired" notification. |
| F4 | On a successful self-delete the user sees the "account deleted" confirmation and is returned to the public users list. |
| F5 | A confirmation dialog is shown before deletion, and dismissing or cancelling it aborts without calling the delete API. |
| F6 | A failed delete (401, 403, 404, or any other error) shows the matching error message and leaves the user signed in. |
| F7 | The delete button in the user-details actions row is constructed with the loaded user's id taken from `UserDetailsCubit` state. |
| F8 | When there is no current user, the ownership guard treats the caller as a non-matching identity and denies the delete. |

## Non-functional Requirements

| ID | Requirement |
|---|---|
| N1 | The `deleteUser` method on `UsersApiClient` is declared as `@DELETE('/user/{user_id}')` with `@Path('user_id') int userId`, and its generated client is regenerated via `build_runner`. |
| N2 | `DeleteUserPort.call` accepts a single `int userId` parameter. |
| N3 | The ownership guard lives in `DeleteUserUseCase` as an `int` comparison (`userId != currentUserId → PermissionDenied`) and is not relocated to the cubit or the UI. |
| N4 | `DeleteUserUseCase.call` takes named parameters `{ required int userId, required int currentUserId }`. |
| N5 | The adapter accepts `int userId`, preserves the double `try`/`catch` with `logger.error` on an unexpected exception, and keeps the 401/403/404/default failure mapping unchanged. |
| N6 | `DeleteUserCubit.confirmAndDelete` takes `int userId` and supplies `currentUserId` from `AuthCubit.currentUser?.id ?? -1` (a non-matching sentinel). |
| N7 | `DeleteUserState` remains a sealed class generated by `freezed` and carries no user identifier. |
| N8 | All UI strings continue to be served via `slang` from the existing `users.delete.*` keys, with no new keys introduced. |
| N9 | The slice imports only `_shared/` and `core/`, and does not import any other slice of the `users` feature. |
| N10 | The cross-slice change is limited to the single `DeleteAccountButton` construction site in `user_details_screen.dart`; the sibling actions-row buttons remain username-keyed. |
| N11 | No observable behavior changes apart from the identifier: the confirmation dialog, success snackbar, navigation target, logout/token handling, and the self-delete rule are unchanged. |
| N12 | The slice ships tests on all four layers (use-case, adapter, cubit, widget) plus an outside-in acceptance test that verifies `deleteUser` is called with the integer id. |
| N13 | No file under `core/` is modified; `AuthCubit` is consumed read-only. |

## Out of scope

- Migrating the sibling actions-row buttons (AssignModerator, UpdateUserTier, EditUser, EraseDbUser) to id.
- Migrating the `user_details` route path or its `@PathParam` (slice 0050).
- Changing `AuthCubit.isMe` or any route, port, or adapter outside the delete vertical.
- All Posts route migrations.
- Any change to the `username` handle, the logout/token behavior, or the self-delete rule itself.
