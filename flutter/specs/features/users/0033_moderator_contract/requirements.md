# 0033 · moderator_contract — Requirements

## Functional Requirements

| ID | Requirement |
|---|---|
| F1 | `UserDto` deserialises the `is_moderator` JSON field into `isModerator: bool`; when the field is absent the value defaults to `false`. |
| F2 | `CurrentUserDto` deserialises the `is_moderator` JSON field into `isModerator: bool`; when the field is absent the value defaults to `false`. |
| F3 | The `User` domain entity exposes a required `isModerator: bool` field. |
| F4 | The `CurrentUser` domain entity exposes a required `isModerator: bool` field. |
| F5 | A moderator badge is shown in the user-details profile header when `user.isModerator == true`, visible to all authenticated users. |
| F6 | The moderator badge is absent when `user.isModerator == false`. |
| F7 | The assign/revoke button is shown in the AppBar actions of the user-details screen only when the viewing user has `Permission.manageModerators`. |
| F8 | Non-superuser authenticated users never see the assign/revoke button on any profile. |
| F9 | When the viewed user has `isModerator == false`, the button is labelled "Assign Moderator". |
| F10 | When the viewed user has `isModerator == true`, the button is labelled "Revoke Moderator". |
| F11 | Tapping "Assign Moderator" sends `PATCH /users/{username}/assign-moderator`. |
| F12 | Tapping "Revoke Moderator" sends `PATCH /users/{username}/revoke-moderator`. |
| F13 | While an assign or revoke request is in flight, a loading indicator replaces the button. |
| F14 | On a successful assign, the button immediately shows "Revoke Moderator" without reloading user-details. |
| F15 | On a successful revoke, the button immediately shows "Assign Moderator" without reloading user-details. |
| F16 | On a failed assign or revoke request, a snackbar error message is displayed. |
| F17 | A 409 response is surfaced as a distinct conflict message, not the generic error. |
| F18 | A 403 response is surfaced as a distinct forbidden message. |
| F19 | `PermissionCubit` emits `Permission.moderatePosts` when `currentUser.isModerator == true` and `isSuperuser == false`. |
| F20 | `PermissionCubit` does not emit `Permission.manageModerators` for moderators who are not superusers. |
| F21 | `PermissionCubit` emits both `Permission.moderatePosts` and `Permission.manageModerators` for superusers (via the existing admin policy). |
| F22 | A regular (non-moderator, non-superuser) authenticated user has neither `Permission.moderatePosts` nor `Permission.manageModerators` in their permission set. |

## Non-functional Requirements

| ID | Requirement |
|---|---|
| N1 | All new UI strings (badge label, button labels, error messages) are defined via slang JSON keys; no hardcoded strings appear in Dart source. |
| N2 | `UserDto.isModerator` and `CurrentUserDto.isModerator` use `@Default(false)` so that API responses that omit the field deserialise without error. |
| N3 | `User` entity is a freezed sealed class; `isModerator` is a required field with no default. |
| N4 | `CurrentUser` is a handwritten `@immutable final class`; `isModerator` is included in the `==` operator and `hashCode`. |
| N5 | `ModeratorManagementAdapter` applies the double-catch pattern: the inner catch handles `DioException` with typed HTTP-status mapping; the outer catch logs via `AppLogger` and returns `Failure.unknown()`. |
| N6 | `AssignModeratorState` is a sealed class generated by freezed with exactly four variants: `initial`, `loading`, `success({required bool isModerator})`, `error(Failure failure)`. |
| N7 | `AssignModeratorCubit` is registered with `@injectable` (not `@lazySingleton`). |
| N8 | `ModeratorManagementAdapter` is registered with `@LazySingleton(as: ModeratorManagementPort)`. |
| N9 | Domain-layer types (`ModeratorManagementPort`, use-cases) import only `dartz`, `freezed_annotation`, and pure Dart packages; no `flutter/*` or `dio/*` imports. |
| N10 | The `moderator_contract` slice does not import any other slice of the `users` feature (only `_shared/` is allowed). |
| N11 | The moderator permission branch is handled inline in `PermissionCubit`; no new `UserRole` is added to `role.dart` or `role_policy.dart`. |
| N12 | `AssignModeratorButton` does not perform its own `Permission.manageModerators` check; the parent screen controls whether the widget is present in the tree. |
| N13 | `UserDetailsCubit` is not reloaded on assign/revoke success; the new `isModerator` value is carried in `AssignModeratorState.success` and applied locally to the displayed user. |
| N14 | `Permission.manageModerators` is added to the `Permission` enum only; `role_policy.dart` is not modified because `admin: {...Permission.values}` already expands to include all enum values. |

## Out of scope

- The pending-posts tab and its `Permission.moderatePosts` gate (slice `pending_posts`).
- The moderation screen and its `moderatePosts` permission gate (slice `moderate_post`).
- Any changes to post entities or post DTOs (slice `post_status_contract`).
- Automatic `GET /users/me` refresh triggered by a role change; the client reflects the new moderator status only after the next login or session refresh.
