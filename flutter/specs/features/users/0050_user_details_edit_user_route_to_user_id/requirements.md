# 0050 · user_details_edit_user_route_to_user_id — Requirements

## Functional Requirements

| ID | Requirement |
|---|---|
| F1 | The user-details deep link shall be `user/:user_id`, parsing an integer id from the URL. |
| F2 | The edit-user deep link shall be `user/:user_id/edit`, parsing an integer id from the URL, behind the existing auth guard. |
| F3 | Opening the user-details route shall load that user's data from the backend `GET /user/{user_id}` route, keyed by the integer id. |
| F4 | The user-details screen shall display exactly the same information as before the migration; only the underlying identifier changed. |
| F5 | The edit-user screen shall load the target user's data via `GET /user/{user_id}` keyed by the integer id. |
| F6 | A non-owner opening the edit-user route shall be blocked, with ownership decided by comparing the current user's id to the target id. |
| F7 | The owner shall be able to change their displayed username (handle) in the edit form and save it, with the new handle sent in the PATCH request body, never in the URL. |
| F8 | Saving an edit shall target the account via `PATCH /user/{user_id}` keyed by the original user's integer id. |
| F9 | The edit-save failure surface shall continue to distinguish 401, 403, 404, 409 (conflict), and 422 (field validation), plus the catch-all. |
| F10 | Navigation from the users list to a user's details shall pass the user's integer id. |
| F11 | The user-menu "my profile" action shall navigate to the user-details route using the current user's integer id. |
| F12 | The detail screen's edit button shall navigate to the edit route using the loaded user's integer id, and re-load the details by that id after returning. |
| F13 | The detail screen's link to a user's posts shall continue to work by passing the loaded user's handle, since posts routes are not yet migrated. |
| F14 | The user-menu "my posts" action shall continue to navigate using the current user's handle. |
| F15 | The edit/delete action buttons shall be shown only when the current user's id equals the displayed user's id. |
| F16 | `AuthCubit.isMe` shall decide ownership by comparing the current user's id to a supplied integer id. |

## Non-functional Requirements

| ID | Requirement |
|---|---|
| N1 | The `username` string used as a stored or displayed handle (`User.username`, `CurrentUser.username`, `UpdateUserRequestDto`/`UserUpdate.username`, `@username` labels, login, create-user form) shall not be migrated to an id. |
| N2 | The shared `UsersApiClient.getUser` and `updateUser` methods shall declare an integer path parameter via `@Path('user_id')`. |
| N3 | The `updateUser` request body shall remain unchanged; only the path identity migrates. |
| N4 | `UserDetailsCubit` and `EditUserCubit`, with their ports, adapters, screens, and routes, shall remain structurally separate slices (no logic merged). |
| N5 | The route page params shall be declared as `int userId` via `@PathParam('user_id')` so auto_route parses the id from the URL. |
| N6 | The sibling `user/:username/posts...` route paths shall remain unchanged. |
| N7 | Each adapter shall retain its catch-all `catch (e, st)` that logs via `logger.error` and returns `UnknownFailure`. |
| N8 | The owner-only edit guard shall exist both in `EditUserCubit.loadInitial` and via the presentation visibility gate, not in UI alone. |
| N9 | `domain/` (ports, use-cases, entities) shall not import Flutter, Dio, or any package outside dartz/freezed/pure Dart. |
| N10 | Cubit state classes shall remain sealed classes generated by freezed; no `setState` is introduced in widgets backed by a cubit. |
| N11 | No new UI strings shall be hardcoded; any text continues to be sourced via slang. |
| N12 | Code that affects codegen (retrofit client, auto_route router) shall be regenerated via `build_runner` so `users_api_client.g.dart` and `app_router.gr.dart` match the new signatures. |
| N13 | No slice outside `user_details`, `edit_user`, the shared API client, and the named core touch-points (`auth_cubit`, `app_router`, `app_shell_screen`, `users_screen`) shall be modified. |
| N14 | No new dependency shall be added to `pubspec.yaml`. |
| N15 | The combined acceptance gate shall verify, against a mocked API client, that read and update are invoked with the integer id; the owner-only outside-in test shall express ownership by id and be updated before the implementation changes. |

## Out of scope

- All Posts route migrations (UserPosts, PostDetails, CreatePost, EditPost, ErasePost) and their `:username` paths, on both the Posts tab and the Users tab.
- The sibling user-action buttons (AssignModerator, UpdateUserTier, EraseDbUser) and GetUserTier, which keep the handle for now.
- Any change to the `username` handle itself (login, `@username` display, the edit form field, the PATCH body) or to `AuthSession`.
- `delete_user` (slice 0049).
