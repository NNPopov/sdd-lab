# Plan: adapt_moderation_log_contract (0039)

## Overview

This is a pure contract-alignment fix — no new cubit, use-case, port, screen, or route.

`ModerationLogEntryDto` declares `actorUserId` and `actorUsername` as required
non-nullable fields, but the backend never includes them in any moderation log entry.
When a post has a non-empty `moderation_log` array, `json_serializable`'s generated
`fromJson` throws because the required keys are absent. The exception is not a
`DioException`, so it bypasses the inner `catch` block, is caught by the outer
`catch (e, st)`, and the adapter returns `Left(Failure.unknown())`. Every screen that
calls `getPendingPosts` or fetches a moderation log shows an error state instead of data.

There is no `0039_adapt_moderation_log_contract/` folder under `lib/features/posts/`.
All changes land in `_shared/` (DTO and entity) and in two presentation widgets owned
by adjacent slices.

## Implementation steps

### Step 1 — Make actor fields nullable in ModerationLogEntryDto

**Modify** `lib/features/posts/_shared/data/dto/moderation_log_entry_dto.dart`.

Change:
```
@JsonKey(name: 'actor_user_id') required int actorUserId,
@JsonKey(name: 'actor_username') required String actorUsername,
```
to:
```
@JsonKey(name: 'actor_user_id') int? actorUserId,
@JsonKey(name: 'actor_username') String? actorUsername,
```

The `required` keyword is removed; the fields become optional with `null` as the
implicit default when the JSON key is absent.

After the edit:
```
dart run build_runner build --delete-conflicting-outputs
```

---

### Step 2 — Make actor fields nullable in ModerationLogEntry entity

**Modify** `lib/features/posts/_shared/domain/entities/moderation_log_entry.dart`.

Change the constructor parameters:
```
required this.actorUserId,   →   this.actorUserId,
required this.actorUsername, →   this.actorUsername,
```

Change the field declarations:
```
final int actorUserId;    →   final int? actorUserId;
final String actorUsername; →  final String? actorUsername;
```

No other fields or logic in `ModerationLogEntry` change. The entity is a plain Dart
class — no codegen needed.

---

### Step 3 — Fix null-unsafe actorUsername read in moderation_log_panel.dart

## What NOT to do

- Do **not** create a new `lib/features/posts/0039_adapt_moderation_log_contract/`
  folder — this fix has no application, domain, or presentation layer of its own.
- Do **not** provide a non-null default value for `actorUsername` in the entity (e.g.
  `''`) — `null` is the honest representation of an absent optional field.
- Do **not** modify any adapter's mapping logic — the pass-through
  `actorUserId: logDto.actorUserId` already compiles once both types are nullable.
- Do **not** touch `PostsApiClient`, any cubit, any state, or any route file.
- Do **not** change `moderation_log_entry_dto.freezed.dart` or
  `moderation_log_entry_dto.g.dart` by hand — regenerate with `build_runner`.
- Do **not** add a fallback empty string inside the entity or adapter; the fallback
  belongs only in the widget layer (`?? ''` on render).
