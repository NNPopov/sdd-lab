# 0035 · moderate_post — Requirements

## Functional Requirements

| ID | Requirement |
|---|---|
| F1 | The moderation screen is reachable at the route path `/pending/:post_uuid/moderate`, nested under `PendingTabRoute`, and guarded by `authGuard` and `PermissionGuard({Permission.moderatePosts})`. |
| F2 | The screen accepts a `PendingPostItem` via the auto_route `extra` parameter and renders the post content immediately, without an additional network request. |
| F3 | The post content view displays the post title, optional media image, and body text in read-only mode with no edit or delete actions. |
| F4 | On displays ≥ 600 dp wide, the post content and moderation panel are rendered side by side in a two-pane layout separated by a vertical divider. |
| F5 | On displays < 600 dp wide, the screen shows a two-tab layout — "Post" and "Moderation" — with the Post tab active by default. |
| F6 | On the wide layout, the moderation log is loaded immediately when the screen mounts. |
| F7 | On the narrow layout, the moderation log is loaded the first time the user switches to the Moderation tab; subsequent tab switches do not trigger a reload. |
| F8 | The moderation log list shows each entry with: an event-type indicator, actor username, formatted timestamp, an action label (Approved / Changes Requested, for `moderator_review` events only), and the entry's message text. |
| F9 | When the moderation log is empty, the log area displays a localised empty-state message instead of an error or blank space. |
| F10 | While the moderation log is loading, a loading indicator is shown in the log area. |
| F11 | The moderation panel contains a multiline text field where the moderator can write a comment. |
| F12 | The moderator can submit an Approve action without providing a message. |
| F13 | The moderator cannot submit a Request Changes action without a non-empty message; attempting to do so displays a localised validation error and makes no network call. |
| F14 | Both the Approve and Request Changes buttons are disabled while a moderation action is in flight. |
| F15 | After a successful moderation action, the screen automatically returns the moderator to the pending list via `context.router.pop()`. |
| F16 | After a successful moderation action, the moderated post is removed from the pending list without a manual refresh, because `PostModeratedEvent` is emitted on `PostEventBus` and `PendingPostsCubit` reacts to it. |
| F17 | A 403 response from the moderation endpoint is presented to the user as a localised permission-denied error message. |
| F18 | A 404 response from the moderation endpoint is presented to the user as a localised post-not-found error message. |
| F19 | A 409 response from the moderation endpoint is presented as a specific localised conflict message indicating the post has already been moderated by another moderator. |
| F20 | Network failures and unexpected errors from the moderation endpoint are presented as a localised generic error message. |
| F21 | The screen and all moderation actions are equally available to users with `Permission.moderatePosts` and to superusers acting as moderators, with no additional configuration. |

## Non-functional Requirements

| ID | Requirement |
|---|---|
| N1 | All UI strings are provided via slang — no hardcoded string literals appear in widget or cubit code. |
| N2 | Both `ModeratePostAdapter` and `ModerationLogAdapter` implement the double-catch pattern: an inner `on DioException` catch maps HTTP errors to typed `Failure` values, and an outer `catch (Object e, StackTrace st)` logs via `AppLogger.error` and returns `Left(Failure.unknown())`. |
| N3 | `IModeratePostPort` and `IModerationLogPort` are narrow interfaces, each declaring exactly one method, located in `moderate_post/domain/ports/`. |
| N4 | `ModeratePostUseCase` enforces the message-required validation client-side before any network call, returning `Left(Failure.validation(...))` when `action == 'changes_requested'` and the message is null or empty. |
| N5 | `ModeratePostState` and `ModerationLogState` are sealed classes generated by freezed. |
| N6 | `ModeratePostCubit` emits `PostModeratedEvent` on `PostEventBus` before emitting the `success` state; the presentation layer never accesses the event bus directly. |
| N7 | Navigation after success (`context.router.pop()`) is handled exclusively in a `BlocListener` in the presentation layer, not inside the cubit. |
| N8 | The `moderate_post` slice does not import any other slice of the `posts` feature; access to shared entities and the API client is limited to `posts/_shared/`. |
| N9 | The `moderate_post/domain/` layer imports nothing from `package:flutter/*`, `package:dio/*`, or any package other than `dartz`, `freezed_annotation`, or pure Dart. |
| N10 | Permission is enforced at two levels: the route guard (`PermissionGuard`) prevents unauthenticated/unauthorised navigation, and the adapter's HTTP mapping converts a 403 response to `ForbiddenFailure`, satisfying the "not only in UI" rule. |
| N11 | `ModeratePostAdapter` is registered with `@LazySingleton(as: IModeratePostPort)` and `ModerationLogAdapter` with `@LazySingleton(as: IModerationLogPort)` in the injectable DI graph. |
| N12 | All DTOs use `@freezed sealed class` with `json_serializable`; no raw `Map<String, dynamic>` parsing is performed inside adapter methods. |
| N13 | The adaptive layout breakpoint is read from `AppBreakpoints.medium` (600 dp) via `LayoutBuilder`; no numeric literal width value appears in the screen widget. |
| N14 | `ModerationLogCubit.load()` is idempotent within a single screen lifecycle: calling it more than once results in at most one network request. |
| N15 | `PostsApiClient` is extended with two new Retrofit-annotated methods (`moderatePost` and `getModerationLog`), and `build_runner` is re-run to regenerate `posts_api_client.g.dart`. |

## Out of scope

- Author's revision flow (slice E, `revise_post`).
- Post-status display in `post_details` (slice F, `post_status_display`).
- Push notifications when a moderation decision is made.
- Moderator editing or deleting post content.
- Pagination of the moderation log (backend returns all entries in one response).
