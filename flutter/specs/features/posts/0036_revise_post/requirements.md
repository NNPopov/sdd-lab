# 0036 · revise_post — Requirements

## Functional Requirements

| ID | Requirement |
|---|---|
| F1 | When a post has `changesRequested` status, the edit screen displays the moderation log alongside the editor. |
| F2 | On wide screens (≥ 600 dp), the edit screen renders the moderation log and the post editor side-by-side in a `Row` separated by a `VerticalDivider`. |
| F3 | On narrow screens (< 600 dp), the edit screen renders two tabs: "Edit" and "Log". |
| F4 | On wide screens the moderation log begins loading immediately when the screen is shown. |
| F5 | On narrow screens the moderation log begins loading the first time the user switches to the "Log" tab. |
| F6 | On narrow screens, switching to the "Log" tab a second time does not trigger a second load. |
| F7 | A revision message field is shown only when `post.status == changesRequested`. |
| F8 | The revision message field is required: submitting a `changesRequested` post with an empty message shows a validation error in the form and is rejected by the use-case. |
| F9 | When `post.status == changesRequested`, the save action calls `PATCH /posts/{post_uuid}/revise` with `title`, `text`, and `message`. |
| F10 | When `post.status == pendingReview`, the save action calls the existing `PATCH /{username}/post/{id}` endpoint; no revision message is sent. |
| F11 | When `post.status == approved`, the Save button is visually disabled (`onPressed == null`). |
| F12 | When `post.status == approved`, a helper text below the disabled Save button explains that the post cannot be edited. |
| F13 | An author with an `approved` post can still open the editor and view the moderation log. |
| F14 | A loading indicator is shown while the revision request is in flight. |
| F15 | After a successful revision the screen emits `PostRevisedEvent` on `PostEventBus` and navigates back via `maybePop()`. |
| F16 | On a 403 response the screen shows a localised "forbidden" error message. |
| F17 | On a 404 response the screen shows a localised "post not found" error message. |
| F18 | On a 409 response the screen shows a localised message telling the author to return to post details and check the current status. |
| F19 | On any other failure the screen shows a generic localised error message. |
| F20 | The moderation log renders each entry's event type, actor username, timestamp, action label, and message. |
| F21 | An empty moderation log displays an empty-state message rather than an error. |
| F22 | When `PendingPostsCubit` receives a `PostRevisedEvent` it calls `refresh()`, causing the revised post to reappear in the pending queue. |

## Non-functional Requirements

| ID | Requirement |
|---|---|
| N1 | All UI strings are delivered via `slang`; no hardcoded strings appear in any widget. |
| N2 | `RevisePostAdapter` implements the double-catch pattern: an inner `on DioException` catch maps HTTP errors to typed `Failure` values; an outer `on Object` catch logs via `AppLogger.error` and returns `Failure.unknown()`. |
| N3 | `edit_post/` does not import from `moderate_post/` or any other peer slice of the `posts` feature; all shared infrastructure lives in `posts/_shared/`. |
| N4 | `IModerationLogPort`, `ModerationLogCubit`, `ModerationLogState`, `ModerationLogAdapter`, and their DTOs are relocated from `moderate_post/` to `posts/_shared/` before `edit_post` is extended; `moderate_post/` imports are updated accordingly and its observable behaviour is unchanged. |
| N5 | `EditPostUseCase` owns the endpoint-routing decision; neither the cubit nor the screen branches on `post.status` to select the target endpoint. |
| N6 | `IRevisePostPort` is a narrow abstract interface with a single method: `Future<Either<Failure, void>> call(UpdatedPostData data)`. |
| N7 | `UpdatedPostData` gains exactly three new fields — `postUuid: String`, `status: PostStatus`, `revisionMessage: String?` — and no other changes. |
| N8 | `EditPostCubit.submit()` signature is unchanged; the cubit state machine remains `initial → loading → success | error(Failure)`. |
| N9 | An empty `revisionMessage` on a `changesRequested` post returns `Left(ValidationFailure)` from the use-case without calling either port. |
| N10 | `RevisePostAdapter` is registered with `@LazySingleton(as: IRevisePostPort)`. |
| N11 | `ModerationLogCubit.load()` is idempotent: repeated calls after the first successful load are no-ops (guarded by the `_loaded` flag). |
| N12 | No business logic appears inside `build()` methods. |
| N13 | `PostEventBus.publish(PostRevisedEvent(...))` is called inside the `BlocListener` on `EditPostSuccess` in the screen widget, not inside the cubit. |
| N14 | `domain/` layer files import only `dartz`, `freezed_annotation`, and pure Dart packages; no `flutter/*` or `dio/*` imports. |
| N15 | `EditPostState` remains a sealed class generated by `freezed`; no new state variants are added. |
| N16 | The `ModerationLogPanel` widget is implemented inside `edit_post/presentation/widgets/`; it does not reuse widgets from `moderate_post/presentation/`. |
| N17 | The `approved` status is not blocked by the use-case; the disabled-button constraint is enforced exclusively in the presentation layer. |
| N18 | `RevisePostRequestDto` is a `@freezed` sealed class with `json_serializable`. |
| N19 | `moderate_post/` logic, state, and presentation files are not changed; only their import paths that reference moved files are updated. |

## Out of scope

- Creating a new top-level route or slice for the revision flow.
- Status display in `post_details` (slice 0037 `post_status_display`).
- Moderator actions (approve / request changes) — slice 0035 `moderate_post`.
- Pending-posts tab and queue management — slice 0034 `pending_posts`.
- An author sending a standalone message without editing post content.
