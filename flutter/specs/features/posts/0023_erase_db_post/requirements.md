# 0023 · erase_db_post — Requirements

## Functional Requirements

| ID | Requirement |
|---|---|
| F1 | The system shall display an erase button on the Post Details screen when the current user is a superuser and is not the author of the post. |
| F2 | The system shall hide the erase button when the current user is the author of the post, regardless of their superuser status. |
| F3 | The system shall hide the erase button completely when the current user is not a superuser. |
| F4 | The system shall present an `AlertDialog` confirmation before executing the erase action. |
| F5 | The confirmation dialog shall state that the erasure is permanent and cannot be undone. |
| F6 | Cancelling the confirmation dialog shall leave the post and the screen unchanged. |
| F7 | While the erase request is in flight, the screen shall display a loading indicator. |
| F8 | While the erase request is in flight, the confirm button shall be disabled to prevent duplicate submissions. |
| F9 | On successful erasure, the system shall display a success snackbar notification. |
| F10 | On successful erasure, the system shall navigate back to the previous screen. |
| F11 | On successful erasure, the erased post shall be removed from the in-memory posts list without a network round-trip. |
| F12 | On erasure failure, the system shall display an error snackbar notification. |
| F13 | On erasure failure, the Post Details screen shall remain open so the superuser can retry or navigate away. |
| F14 | The use-case shall return `Left(Failure.permissionDenied())` when `isSuperuser` is `false`, regardless of how the call was initiated. |
| F15 | The erase feature shall function correctly regardless of how the user arrived at the Post Details screen (posts list, deep link, or other navigation path). |

## Non-functional Requirements

| ID | Requirement |
|---|---|
| N1 | The slice follows the vertical-slice layout: `domain/` → `data/` → `application/` → `presentation/` inside `lib/features/posts/erase_db_post/`. |
| N2 | `EraseDbPostState` is a sealed class generated by `freezed` with five variants: `initial`, `confirming`, `deleting`, `success`, `failure(Failure)`. |
| N3 | `EraseDbPostCubit` is registered with `@injectable` and receives `EraseDbPostUseCase`, `AuthCubit`, and `PostEventBus` via constructor injection through `get_it`. |
| N4 | `EraseDbPostUseCase` accepts `isSuperuser` as a required named call-site parameter; it does not read auth state directly. |
| N5 | `EraseDbPostPort` is a Dart `abstract interface class`; `domain/` does not import `package:flutter/*`, `package:dio/*`, or any package outside `dartz`/`freezed`/pure Dart. |
| N6 | `EraseDbPostAdapter` is annotated `@LazySingleton(as: EraseDbPostPort)` and implements the double-catch pattern per `agent_docs/error_handling.md`. |
| N7 | The adapter outer catch (`catch (e, st)`) calls `AppLogger.error` and returns `Left(Failure.unknown())`; the inner catch maps `DioException` status codes 401→`unauthorized`, 403→`forbidden`, 404→`notFound`, `5xx`→`serverError`. |
| N8 | `EraseDbPostCubit` publishes `PostDeleted(id)` to `PostEventBus` on success; it does not modify `PostEventBus` or `PostEvent`. |
| N9 | `EraseDbPostButton` owns its own `BlocProvider<EraseDbPostCubit>` internally and is fully self-contained; no `EraseDbPostCubit` provider is added to `post_details_route.dart`. |
| N10 | On success, the button widget calls `context.router.pop()`; it does not call `replaceAll` and does not invoke `forceLogout`. |
| N11 | All user-visible strings are delivered via `slang` keys under `posts.eraseDbPost`; no string literals appear in the widget layer. |
| N12 | Localisation keys `tooltip`, `confirmTitle`, `confirmMessage`, `confirmButton`, `cancelButton`, `success`, `errors.forbidden`, and `errors.generic` are added to both `en.json` and `ru.json`. |
| N13 | `erase_db_post` does not import any other slice of the `posts` feature; only `_shared/` is allowed as a cross-slice dependency. |
| N14 | No class within this slice is named `*Repository`; the port/adapter naming convention is used throughout. |
| N15 | No new dependency is added to `pubspec.yaml` without explicit user approval. |
| N16 | `dart format .` produces no diff, and `dart analyze` produces no warnings after implementation. |
| N17 | `dart run build_runner build --delete-conflicting-outputs` is run after modifying `posts_api_client.dart` and after modifying i18n JSON files. |
| N18 | Tests cover all four layers: use-case (unit), adapter (unit), cubit (`bloc_test`), and widget (`flutter_test` with mocked cubit). |

## Out of scope

- Erasure triggered from the posts list screen (no swipe-to-delete for superusers on list tiles).
- Bulk erasure of multiple posts.
- Audit log or moderation history for erased posts.
- Push notification to the post author when their post is erased.
- Soft delete, trash, or undo functionality.
- Erasure by non-superuser moderator roles.
- Updating the paginated post count after erasure.
