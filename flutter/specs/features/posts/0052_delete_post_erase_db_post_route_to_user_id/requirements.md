# 0052 · delete_post_erase_db_post_route_to_user_id — Requirements

## Functional Requirements

| ID | Requirement |
|---|---|
| F1 | The author of a post can delete it from the post-detail screen, and the request targets the id-based route `DELETE /{user_id}/post/{id}` with the author's integer `user_id`. |
| F2 | A superuser who is not the author can erase any post from the database, and the request targets the id-based route `DELETE /{user_id}/db_post/{id}` with the author's integer `user_id`. |
| F3 | A delete attempt is refused with a forbidden failure, before any network call, when the current user's id does not equal the target `user_id` (or there is no current user). |
| F4 | An erase attempt is refused with a permission-denied failure, before any network call, when the current user is not a superuser. |
| F5 | The Delete button is shown on the post-detail screen whenever the current user is the author (`currentUser.id == userId`), regardless of whether the loaded post carries a handle. |
| F6 | The Erase button is shown on the post-detail screen whenever the current user is a superuser who is not the author, regardless of whether the loaded post carries a handle. |
| F7 | A user who is neither the author nor a superuser sees no Delete and no Erase action on the post-detail screen. |
| F8 | The Edit button continues to show for the author and addresses the post by `user_id`, unchanged from slice 0051. |
| F9 | The delete confirmation dialog, success snackbar, and automatic pop to the previous screen behave exactly as before the migration. |
| F10 | The erase confirmation dialog, success snackbar, and automatic pop to the previous screen behave exactly as before the migration. |
| F11 | On a successful delete or erase, a `PostDeleted` event carrying the post id is published, unchanged. |
| F12 | Delete and erase failures (unauthorized, forbidden, not found, server, network, unexpected) surface the same user-facing messages as before the migration. |

## Non-functional Requirements

| ID | Requirement |
|---|---|
| N1 | The `deletePost` and `eraseDbPost` API methods declare an `@Path('user_id') int userId` path parameter on the templates `/{user_id}/post/{id}` and `/{user_id}/db_post/{id}`; no other `PostsApiClient` method changes. |
| N2 | `DeletePostPort`, `DeletePostUseCase`, and `DeletePostCubit.confirmAndDelete` carry `int userId` instead of `String username`. |
| N3 | `EraseDbPostPort`, `EraseDbPostUseCase`, and `EraseDbPostCubit.confirmAndErase` carry `int userId` instead of `String username`. |
| N4 | The delete ownership guard is expressed as `currentUser == null || currentUser.id != userId` and returns the existing `Failure.forbidden` with its current message unchanged (not `Failure.permissionDenied`). |
| N5 | The erase superuser guard is unchanged and returns `Failure.permissionDenied` for a non-superuser. |
| N6 | The `DeletePostButton` and `EraseDbPostButton` widgets take `int userId` and forward it to their cubit. |
| N7 | The `post_details` action row passes the route `userId` (the author id) to both buttons and no longer reads `postState.post.username`; the `handle != null` visibility guards are removed. |
| N8 | No part of `post_details` other than the action row changes; the read path migrated in 0051 is untouched. |
| N9 | Both DELETE requests remain body-less; tooltips, dialogs, and success/forbidden messages are unchanged (no new or modified UI strings). |
| N10 | No `auto_route` page, route path, or `@PathParam` is added or changed for delete/erase; neither vertical owns a route. |
| N11 | Each adapter retains its catch-all `on Object catch (e, st)` that logs via `logger.error` and returns `UnknownFailure`, with its HTTP failure mapping preserved (`deletePost`: 401/403/404/network; `eraseDbPost`: 401/403/404/≥500/network). |
| N12 | All slice state classes remain sealed classes generated by freezed, unchanged in shape. |
| N13 | The slice imports no other slice of the posts feature; only `_shared/` and `core/` are referenced. |
| N14 | `build_runner` regenerates `posts_api_client.g.dart` after the retrofit signature change; no DTO, freezed, or router regeneration is required by this slice. |
| N15 | No handle (`Post.username`, `CurrentUser.username`, `@username` labels) is migrated to an id, and no `username` field is added to `PostDto`. |

## Out of scope

- `user_posts` and `create_post` route migration (slice 0053); `getUserPosts` and `createPost` stay username-keyed.
- `getPost` / `patchPost` and the `post_details`/`edit_post` read/update path — migrated in 0051.
- The `created_by_user_id` DTO contract (made required in 0051) and any other DTO shape.
- `post_uuid`-based routes (`revisePost`, `moderatePost`, `getModerationLog`) — never carried a username.
- The DELETE request semantics, confirmation dialogs, success/forbidden messages, the `PostDeleted` event, and `AuthSession`.
