# Handoff: кросс-платформенная конфигурация Flutter/Dart + get_it

> Сводка обсуждения для передачи свежему агенту. Это была консультация (Q&A), а не кодовая задача — артефактов, коммитов и diff-ов нет, поэтому ниже зафиксированы решения и открытый вопрос, а не статус незавершённой работы.

## Контекст
Как организовать универсальную конфигурацию для Flutter-приложения, таргетящего **mobile / desktop / web SPA**, с инъекцией зависимостей через **get_it**. Цель пользователя — единый подход к параметрам конфигурации приложения для всех платформ.

## Обсуждённые решения
- **Три слоя, которые нужно разделять:** (1) env-конфиг dev/staging/prod, (2) платформо-зависимые реализации сервисов, (3) сборка DI-графа.
- **`AppConfig`** как платформо-независимая абстракция + реализации `DevConfig` / `StagingConfig` / `ProdConfig`.
- **Определение платформы:** через `kIsWeb` + `defaultTargetPlatform` из `package:flutter/foundation.dart`. НЕ использовать `dart:io Platform` — ломает веб-сборку на этапе компиляции.
- **Платформо-зависимые реализации:** через conditional imports (`if (dart.library.io)` / `if (dart.library.js_interop)`) + stub-файл. Гарантирует, что нативный код не попадёт в веб-бандл и наоборот.
- **Сборка графа:** функция `configureDependencies(AppConfig)`, внутри — `registerSingleton<AppConfig>`, платформенные сервисы через фабрику, lazy-синглтоны с зависимостью от конфига, опциональная регистрация по платформе, `await getIt.allReady()`.

## Ключевая проблема и рекомендация (главное в этой сессии)
- **Проблема:** пользователь использует `flutter_dotenv` (`.env`), но он не подходит для веба — файл грузится как ассет в рантайме, публично доступен по URL в бандле и загружается асинхронно. Хардкод предложили как альтернативу, но он не годится для мобилок (негибко).
- **Рекомендация:** перейти на **`--dart-define-from-file`** — compile-time, работает одинаково на всех платформах, поддерживает tree-shaking. JSON-файл на окружение (`config/dev.json`, `config/prod.json`), запуск `flutter run/build ... --dart-define-from-file=config/<env>.json`. Чтение через `String.fromEnvironment` / `bool.fromEnvironment` / `int.fromEnvironment`. DI после этого не требует `await dotenv.load()` — значения доступны синхронно на старте.
- **Каветат по безопасности (важно):** на вебе НИ ОДИН клиентский подход не прячет секреты — dart-define, dotenv и хардкод одинаково попадают в JS-бандл открытым текстом. Не-секретные параметры (URL-ы, фичефлаги, таймауты) — ок через dart-define-from-file; настоящие секреты должны жить на бэкенде, клиент ходит через прокси.

## Открытый вопрос → фокус следующей сессии
Последний заданный пользователю вопрос **остался без ответа**: что именно лежит в его `.env` — только URL-ы и фичефлаги, или есть секретные ключи, которые он пытается скрыть?
- Если только не-секретные параметры → достаточно миграции `dotenv → dart-define-from-file`.
- Если есть секреты → часть параметров надо убирать с клиента (особенно для веба) и проксировать через бэкенд.

## Предлагаемые следующие шаги
1. Дождаться ответа про содержимое `.env`.
2. По ответу выдать либо пошаговый план миграции на `dart-define-from-file`, либо проработать вынос секретов на бэкенд.
3. (Опционально) Рассмотреть `injectable` поверх `get_it` с аннотацией `@Environment(...)` для платформенных модулей, если граф зависимостей большой.
4. (Опционально) Паттерн для CI: gitignore `config/*.json` с реальными значениями, коммит `config/dev.example.json` как шаблон, генерация рабочего JSON из секретов CI перед сборкой.
